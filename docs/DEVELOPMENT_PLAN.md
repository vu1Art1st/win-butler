# Win-Butler 开发实施方案

修订日期：2026-11-26

## 目标与约束

本文件是唯一的全产品开发计划，包含功能范围、阶段顺序、验收标准和每期可直接使用的 AI 提示词。它以现有 Win-Butler 初版方案和 demo 为起点，逐步实现下列工具的主要功能，并保持一个可在本机正常构建、启动和使用的原生 Windows 桌面程序。进入每一期前，AI 必须先阅读根目录 [`AGENTS.md`](../AGENTS.md)、本文件及相关现有代码，遵循仓库已经采用的构建系统、UI 技术和目录结构。上下文菜单模块的详细数据模型和写入设计见 [`CONTEXT_MENU_TECHNICAL_DESIGN.md`](CONTEXT_MENU_TECHNICAL_DESIGN.md)。

UI 采用“原生桌面工作台”方向，参考用户提供的浅色窄侧栏、紧凑页头、列表/详情和状态栏示意，不复制其 PCAP 业务内容。全局字体、字号、颜色、DPI、圆角、阴影、间距和交互约束统一位于 [`AGENTS.md`](../AGENTS.md) 的 **UI visual specification**；本文件负责页面结构、UI 与 Shell 的同步顺序和逐期提示词，不维护第二份互相竞争的视觉规范。UI 是原生 C++/EUI-NEO 实现，不新增 HTML、CSS、Electron、WebView 或浏览器验收要求。

- 应用保持原生 C++，不引入 Electron 或 WebView。
- 优先复用现有 demo 的技术栈。UI 改造以共享控件、布局、图标、字体、颜色和交互规范为主，不因视觉更新重写无关功能。
- 主要验收是当前开发机上的构建成功、程序能启动、主要流程能实际操作。取消端到端测试、浏览器自动化和完整 UI 自动化测试要求；不为此创建新的测试目录或测试框架。
- 系统配置变更必须明确目标、影响和权限；高影响操作在提交前预览，并尽可能导出备份、验证变更结果和提供恢复入口。
- 所有“全功能”以每期开始时整理出的官方功能清单和逐项验收表为准，不依据产品名称或宣传语猜测。系统版本不支持的功能要在 UI 中标出原因，不可伪报成功。
- 参考项目只用于功能调研。不得复制 GPL 等许可证项目的代码到本项目，除非先确认并接受相应许可证义务；优先基于公开行为、Windows API 和自有实现重做。

## UI 技术建议

纯 C++ 且不使用 WebView 时，建议先审查现有 demo 使用的窗口/UI 框架和启动、空闲资源数据，再决定是否迁移。对常驻或经常打开的系统工具，低资源和易维护通常比完全自绘更重要。

- 若 demo 已有可维护的原生 C++ UI 框架，保留它，补齐统一设计规范、可复用控件、键盘操作、DPI 适配和系统主题支持。
- 若目前是 Win32/WTL，且资源占用是首要约束，优先保留 Win32/WTL，使用系统控件与视觉样式，并在必要处用 Direct2D/DirectWrite 做少量自绘。代价是 Fluent 风格控件和复杂布局需要自行实现。
- 若 demo 尚无合适的 UI 框架，并且更看重现代 Windows 视觉和可维护性，可评估 C++/WinRT + WinUI 3。它不使用 WebView，但 Windows App SDK 的部署和运行时开销高于简单 Win32；需用真实 demo 做发布体积、冷启动、空闲 CPU 和内存对比后再定。
- Qt Widgets 也是原生 C++、不依赖 WebView 的成熟选择，但引入 Qt 运行时与部署体积，视觉风格也不等同 WinUI。只有在项目已经使用 Qt 或评估后能明显降低 UI 开发成本时再选择。
- 不建议为追求“现代”而一次性更换整套框架。先建立窄侧栏导航、工作区列表/详情、状态栏、轻量设置页等应用级规范，再逐个迁移模块。

当前仓库已采用 C++20、CMake 3.24+、x86 Win32 和 EUI-NEO v0.6.5，M0 已验证该 UI 可构建、启动并正确处理 150% DPI。因此建议继续使用 EUI-NEO，不迁移到 Qt、WinUI 3 或自绘框架；先补齐现有组件和页面组织。只有后续功能被 EUI-NEO 明确阻塞时，才基于可复现的构建/交互问题重新评估技术栈。

建议记录冷启动时间、稳定空闲 60 秒的进程 CPU、私有工作集和发布目录体积。M0 当前记录了扫描耗时约 60 到 140 ms，但这不是应用启动/空闲资源数据；资源预算以本机实测为准。

### UI 架构与同步开发约定

- 保留 `src/app/` 负责 EUI-NEO 窗口、页面组合、视图状态和交互，`src/shell/` 负责扫描、归一化、能力判断、事务和系统状态查询。应用层只消费不可变结果/快照，不自行拼接注册表路径、猜测菜单生效状态或执行 Shell 写入。
- 在现有 UI 文件中按实际需要提取共享主题 token、图标映射、导航项、页头、搜索/筛选栏、表格、详情面板、状态条、确认/错误对话框等；不要为每个小控件建立目录。新增源文件必须放在已有行为归属的 `src/app/` 或 `src/shell/` 下，并接入现有 CMake target。
- Shell 模块先定义稳定 DTO/枚举/诊断字段和能力矩阵，UI 以该契约并行实现布局；后台任务返回只读快照，UI 线程负责选择、筛选和渲染。未提供的数据用明确的“尚未扫描/未知/不支持”状态，不能用演示数字或假成功替代。
- 每个功能期的顺序是“契约与只读查询 → 页面和交互 → 有快照的写入/恢复 → 本机构建启动检查”。可以在同一期并行推进 UI 和 Shell，但不能把 UI 完成等同于系统功能完成。
- 参考截图中的多层卡片、威胁评分和模块矩阵不直接搬入 Win-Butler；系统工具页面优先信息密度、可扫描性、撤销入口和错误可见性。页面设计需经过实际 Windows 构建/启动及 100%、150% 等可用 DPI 的人工检查。

## 功能范围

### 上下文菜单管理

以 ContextMenuManager 的功能范围为对照，覆盖文件、目录、桌面/背景、驱动器、文件类型及全局 Shell 上下文菜单项；按现代菜单和经典/传统菜单分组显示，支持扫描、搜索、筛选、启用/禁用、重命名、改图标、编辑可编辑项、删除、自定义菜单项、导出/恢复、导航至对应注册表位置和文件位置等已有参考功能。识别新建（New）、发送到（Send To）、打开方式（Open With）、WinX 及系统仍保留的 IE 菜单来源，并在首期功能盘点后列出实际支持项；当前 Windows 已移除的场景应标为不适用。

菜单条目主标题应显示 Shell 解析出的友好名称，图标应从命令、默认图标、资源 DLL 或 Shell 元数据解析。注册表路径、值名、CLSID 和原始命令放在详情/诊断区域，不能直接作为用户看到的主要名称。必须保留扩展类型、注册位置、适用对象、菜单类别、原始注册数据、图标来源和当前状态，避免将不同注册机制混为一类。

### Win11 菜单样式切换

提供经典/传统右键菜单与 Windows 11 默认现代菜单的切换、状态检测、必要的 Explorer 重启提示及命令行操作（若参考工具支持的参数已在调研中确认）。按 Windows 版本和系统构建号检测兼容性，保留键值备份并提供恢复。该功能通过注册表修改系统行为，需明确告知用户并在执行前确认。

截至本方案修订日，Sordum 页面发布了 2026-11-24 更新的 v1.3，并说明为 Windows 11 26H2 的第二个 CLSID 添加了修复。因此实现不可只硬编码旧版单一 CLSID；必须在目标 Windows 构建上验证状态识别和切换结果。

### Windows Update Blocker

覆盖 Windows Update 服务状态、启用/禁用并应用、保护服务设置、`Wub.ini` 中附加服务列表（最多 25 项）、Windows Update 计划任务列表、更新相关进程的阻止/解除阻止/关闭配置、打开 Windows 服务管理器和更新疑难解答，以及命令行参数。显示服务系统显示名和内部名，并把只读显示项与可编辑项区分开。进程阻止/关闭可能造成系统不稳定，必须逐项说明目标并二次确认。参考工具不阻止 Microsoft Defender 更新，产品说明中要写清这一限制。变更前保存服务、计划任务和进程策略的旧值；恢复必须还原具体旧值。

### Registry Key Jumper

覆盖选中文本/剪贴板路径识别、Ctrl+Alt+X 可配置热键、剪贴板快速跳转、收藏夹增删、导入/导出/HTML 导出、搜索、跳转、重复项删除、桌面快捷方式、置顶、启动时隐藏、托盘菜单、启动注册表编辑器或用户指定的编辑器，以及可选的桌面/“此电脑”上下文菜单入口。支持常见注册表根键别名和 `HKEY_*` 全名；输入含有路径前后缀、引号或 `.reg` 文件格式时应正确提取或给出错误。打开注册表编辑器不等于本程序可以越权写注册表；收藏夹及跳转默认不修改目标键。

### Drive Icon Manager

覆盖参考程序针对“此电脑”和资源管理器侧边栏中的第三方网盘/应用命名空间图标清理：枚举当前用户 SID 对应的注册位置、解析并显示项目名称、选中后删除、按项备份和恢复 `.reg` 数据。另包含通过修改注册表权限阻止图标再次写入的能力。删除和 ACL 锁定都是高风险操作，必须展示 SID、精确注册表路径和选中项，先备份；保存原始 DACL 并实现验证过的解锁/恢复流程。无法可靠恢复权限时，应将锁定功能标记为不支持，不能提供不可逆的一键开关。

### WinTune

以参考仓库当前 README、配置样例和源码中的工具清单为逐项实现依据，覆盖系统/隐私/Explorer/可选优化、启动项管理、Hosts 编辑、清理开始菜单、功能提示、JSON 配置保存/载入、截图保存、主题和多语言。兼容确认后的命令行能力包括切换用户（`/User`）、导出配置（`/SaveConfig`）和导入配置（`/LoadConfig`）。每项 tweak 使用稳定 ID、适用 Windows 版本、当前值、目标值、权限、备份及恢复策略。配置文件兼容性、参数边界和版本要通过源码/文档确认后再实现；旧系统或策略管理的设置应显示“不支持/被策略控制”，而不是直接覆盖。

### Advanced Renamer

该工具范围远大于一个批量重命名对话框。逐项盘点参考版本的批处理模式、方法、标签、导入导出和脚本能力；分多个里程碑实现：

- 批次工作区：添加文件/目录、拖放、排序、过滤、文件对、保存/载入批次、目标模式（重命名、复制、移动）和冲突处理。
- 方法链及即时预览：实现官方清单中的 Add、List、List Replace、Move、New Case、New Name、Remove、Remove Pattern、Renumber、Replace、Script、Swap、Timestamp、Trim 方法；允许调整顺序、启停、复制和删除方法。方法细节按 Advanced Renamer 文档逐项核对。
- 条件与正则：正则替换/匹配、条件过滤、冲突检测、非法文件名字符处理以及大小写/Unicode 边界。
- 元数据标签：文件系统属性，以及图片、音频、视频、文档和可访问的 EXIF/IPTC/GPS 标签。每类标签逐项记录依赖、缺失元数据和读取失败行为；不允许默默产生空名称。
- 脚本及集成：如参考版本包含脚本方法、命令行、外部元数据工具或项目导入导出，则单独盘点沙箱/权限/依赖与兼容格式后实现。脚本执行需有明确能力边界、错误位置和预览，不得在无确认时直接批量改文件。
- 执行与撤销：提交前列出旧名/新名/目标路径，检测重名、覆盖、跨卷移动及锁定文件；失败时报告部分成功清单，并对已执行的动作提供可验证撤销记录。

首期不要求复制参考软件的布局或营销功能，但必须以清单逐项跟踪功能覆盖情况。

### Firewall App Blocker

覆盖拖放/浏览添加程序、进程多选、入站/出站分别建规则、允许/阻止/启用/禁用/删除、规则排序、白名单模式、允许本地子网、参考菜单中的“阻止互联网/限制防火墙选项”、本地化、命令行参数，以及可配置的 Explorer `.exe` 右键集成（可要求按住 Shift 才显示）。枚举参考工具的“Netsh Commands”菜单并逐项记录能力。优先通过 Windows Firewall COM API 读取和管理规则，不依赖解析本地化命令行输出。展示规则配置文件、程序完整路径、方向、动作、启用状态和来源；提示该功能依赖 Windows 防火墙开启、不修改 Windows 防火墙默认规则，并检测第三方防火墙/组策略限制。白名单模式会改变大量程序的联网行为，必须有二次确认、前后状态快照和一键恢复。

### NeoHtop（候选）

在阶段评审时单独决策。当前 NeoHtop 项目采用 Tauri/Svelte，直接嵌入会引入 WebView，与本项目约束冲突。因此本计划不将其作为必须合并的代码依赖。若确需集成，可先提供可选外部启动入口；如需内嵌监控页面，则用原生 C++/Windows API 重新实现明确选定的指标，并将其作为单独可选模块评估资源开销和维护成本。

## 分期实施与 AI 提示词

下列提示词可单独复制给 AI 执行。每期提示词都要求先理解现有实现，再在当前仓库内完成该期工作；不得同时跨期开发。阶段顺序允许因仓库现状微调，但安全底座、菜单数据模型和功能清单必须先于高风险写操作。

### 第 0 期：仓库审计与功能基线

**交付**：确认构建方式、入口、UI 框架、目录职责、已有 demo 功能、已有数据模型、支持的 Windows 版本、发布方式和资源基线；建立逐项功能矩阵、风险表、依赖表和阶段缺口。仅补充现有文档，不重构代码。

**验收**：每项参考功能有来源和实现/待实现状态；每个高风险功能有权限、备份、恢复和本机验证要求；技术选择尊重现有仓库而非假定。

**提示词**

```text
你正在 win-butler 仓库中完成第 0 期审计。先完整阅读根目录 AGENTS.md、docs/DEVELOPMENT_PLAN.md、README、现有构建文件、源代码目录和 git status，再检查当前 demo 的实际行为。不要改代码，不要创建目录，不要编造当前实现。

基于以下参考资料逐个核实可访问的 README/官方文档/功能页面：ContextMenuManager、Sordum Windows 11 Classic Context Menu、Windows Update Blocker、Registry Key Jumper、Drive Icon Manager、WinTune、Advanced Renamer Getting Started、Firewall App Blocker、NeoHtop。为每项功能记录：参考版本/来源、具体能力、关联 Windows API 或外部依赖、所需权限、数据持久化、备份/撤销、兼容限制、与现有 demo 的差距。对来源没有说明的内容标为待核实，不要猜。

审计现代菜单与经典菜单的 Shell 注册机制，记录“菜单类别、适用对象、友好名称、图标来源、注册位置、启用状态”所需字段。检查现有 UI 技术和目录后，给出保持现状、Win32/WTL、C++/WinRT + WinUI 3、Qt Widgets 的实际取舍，并说明不使用 Electron/WebView。记录原 demo 冷启动、稳定空闲 CPU、内存和发布体积的测量方法；能在当前机器测量时写入数据，不能时写清阻塞原因。

在现有 `docs/REFERENCE_ANALYSIS.md` 中更新功能矩阵和审计结论，不创建新目录，遵守 AGENTS.md，不加端到端测试。最后报告发现、未决问题、将要进入的下一期及本机检查结果。
```

### 第 1 期：应用导航、术语和 UI 基础

**交付**：在 demo 现有 EUI-NEO 框架上建立浅色工作台外壳：左侧模块导航、顶部页面标题与操作区、可滚动内容区、右侧/下方详情面板和底部状态栏。提取共享主题 token、图标、间距、字体、焦点和反馈控件；完善搜索/筛选、轻量数据表格、空/加载/错误/无权限状态和确认对话框，制定术语表并修正“传统动词”等非标准词汇。以真实只读 Shell 扫描快照驱动首个页面，支持高 DPI、键盘焦点和 Windows 主题。

**验收**：所有计划模块有清楚入口或明确“尚未实现”状态；上下文菜单页能看到真实名称/类型/场景/状态/来源和详情，不显示演示计数；启动和闲置资源不出现明显回归；不引入 WebView 或未经评审的新 UI 框架；界面上用户可见标签使用中文计算机词汇，必要时提供英文原名。人工检查最小窗口、150% DPI、长路径截断、键盘导航及扫描失败状态。

**提示词**

### 第 11 期：Firewall App Blocker

**交付**：程序选择/添加，入站出站规则、允许/阻止/启停/删除、白名单模式、刷新及参考命令行/Explorer 集成。

**验收**：按程序路径和方向正确显示规则；白名单切换有快照和恢复；系统策略冲突有明确说明。

**提示词**

```text

实现拖放/文件选择器添加程序、进程多选、按完整路径列出现有规则、创建入站/出站阻止/允许规则、启用/禁用/删除、排序、刷新、白名单模式、允许本地子网、阻止互联网/限制防火墙选项、Netsh Commands 菜单及官方支持的命令行能力。Explorer 集成需支持 `.exe` 右键添加并可设置 Shift 键门槛；安装/移除要备份原注册表并能恢复。显示规则名称、程序路径、方向、动作、配置文件、启用状态和策略来源。使用 COM API 对规则读写并检查 HRESULT、权限和策略冲突；提示依赖 Windows 防火墙开启，且规则不覆盖默认 Windows 防火墙规则。

白名单模式属于高影响操作：先解释可能阻断哪些程序的网络，保存相关规则快照，显示预览并二次确认；应用后验证有效策略并提供恢复入口。不要自行关闭防火墙服务或调整网络安全策略。先做只读本机规则检查；如需写规则，使用可移除的临时规则并确认恢复。构建并启动，不添加 E2E。
```

## 阶段依赖与交付纪律

建议顺序为：第 0 期审计 → 第 1 期 UI 外壳与只读契约 → 第 2 期上下文菜单 UI/Shell 同步 → 第 3 期菜单样式 → 第 4/5 期服务和注册表跳转 → 第 6/7 期驱动器图标与系统调整 → 第 8/9/10 期批量重命名 → 第 11 期防火墙 → 第 12 期 NeoHtop 决策与本机收尾。每个功能期均允许 UI 与 Shell 并行，但先冻结数据契约和状态语义；若仓库现有结构需要调整顺序，先更新矩阵和依赖说明。

每期完成时只报告：功能矩阵状态、修改文件、本机构建与启动结果、需要管理员权限的操作、已知兼容限制和下一期依赖。合并阶段成果前确认用户现有工作未被覆盖。无实际运行证据时，明确标为“未验证”，不要宣称完成。
